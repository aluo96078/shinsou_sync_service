# 規格：分享、追蹤與封鎖（P4）

同一個伺服器內的帳號可以互相分享書庫裡的作品。API 契約在 [`api/openapi.yaml`](../../api/openapi.yaml)（標籤 `social`），資料表在 `migrations/00003_sharing.sql`。本文件說明契約沒寫出來的規則。

所有端點都需要登入，並受信箱驗證限制（見 [web.md](web.md) 第 3 節）。

## 1. 功能開關

- 實例設定 `sharing`（`enabled` / `disabled`），環境變數 `SHINSOU_SHARING`，預設 `enabled`；管理員可在後台即時切換。
- `GET /.well-known/shinsou` 的 `features.sharing` 反映目前的值。
- 關閉時，`/api/v1/shares*` 全部回 `403 feature_disabled`；已存在的分享保留，重新開啟後照常可見。
- 使用者搜尋、追蹤、封鎖與 `/me/sharing` 不受這個開關影響（評論功能也會用到追蹤與封鎖）。

## 2. 使用者搜尋

`GET /api/v1/users?q=` 以使用者名稱**前綴**比對（不分大小寫），依名稱排序，最多 50 筆。

不會出現在結果中的帳號：

- 呼叫者自己；
- 已停權的帳號；
- 封鎖了呼叫者的帳號（對方封鎖你之後，你就找不到對方）。

結果只含 `id` 與 `username`，以及呼叫者與對方的關係（`following`、`followsYou`、`blocked`、`canShare`）。信箱等其他資料不會外流。

搜尋與建立分享共用每個帳號的速率限制 `SHINSOU_SOCIAL_RATE_PER_MINUTE`（預設 120，突發 `SHINSOU_SOCIAL_RATE_BURST` 預設 40；0 = 不限制），超過回 `429 rate_limited`。

## 3. 追蹤

- 追蹤是單向的，不需要對方同意，也不會通知對方。
- 不能追蹤自己（`422`）、已停權或封鎖了你的帳號（`404`，兩者不區分）、你封鎖中的帳號（`409 user_blocked`，要先解除封鎖）。
- 追蹤的用途：對方把接收設定設為「只接受追蹤對象」時，只有對方追蹤的人能分享給對方。

## 4. 封鎖

封鎖一個帳號時，在同一個交易內：

1. 雙方互相的追蹤關係都移除；
2. 對方寄給你、還沒回應的分享全部標為 `dismissed`。

封鎖之後，對方：

- 搜尋不到你；
- 不能追蹤你（`404`）；
- 不能分享給你（`403 share_refused`，與「對方不接受分享」同一個代碼，所以對方無法確定自己被封鎖）。

解除封鎖不會恢復追蹤關係，也不會恢復被標為 `dismissed` 的分享。

## 5. 接收設定

`/api/v1/me/sharing` 的 `receiveFrom`：

| 值 | 誰能分享給我 |
|---|---|
| `everyone`（預設） | 任何沒被我封鎖的帳號 |
| `following` | 只有我追蹤的帳號 |
| `nobody` | 沒有人 |

`UserSummary.canShare` 是「現在分享給對方會不會被接受」的結果：功能開啟、雙方沒有封鎖關係，且符合對方的接收設定。

## 6. 分享

### 6.1 建立

`POST /api/v1/shares`，內容是收件者 `recipientId`、作品雜湊 `work`、選填的 `message`。

- 作品必須在寄件者的書庫裡（有一筆未刪除、鍵等於該雜湊的 `library` 記錄）。本機匯入的書（`local:`）沒有可攜的身分，不能分享，回 `422 unknown_work`。
- `message` 是純文字，最長 500 字元，前後空白會去掉；前台一律當純文字顯示，不解析 Markdown 或連結。
- 同一位寄件者對同一位收件者、同一部作品，同時只會有一筆 `pending` 的分享；重複送出回 `200` 與原本那一筆（訊息不更新）。
- 每個帳號每 24 小時最多建立 `SHINSOU_SHARES_PER_DAY` 筆分享（預設 200；0 = 不限制），超過回 `429 rate_limited`，`retryAfterSeconds` 是最舊那一筆滿 24 小時所需的秒數。重複送出不計入。

檢查順序：功能開關 → 速率限制 → 輸入格式 → 不能分享給自己（`422`）→ 收件者存在且未停權（`404`）→ 呼叫者是否封鎖收件者（`409 user_blocked`）→ 收件者是否接受（`403 share_refused`）→ 作品在書庫中（`422 unknown_work`）→ 每日上限。

封鎖、追蹤與建立分享都會先依帳號 `id` 順序鎖住雙方的使用者資料列，所以「封鎖」和「對方同時送出分享」不會交錯：分享不是在封鎖前建立（然後被封鎖標為 `dismissed`），就是在封鎖後被拒絕。

### 6.2 狀態

```
pending ──accept──▶ accepted
   │                   ▲
   └──dismiss──▶ dismissed ──accept──┘
```

- `accept`：只有收件者可以呼叫。伺服器替收件者寫入一筆 `library` 記錄（見 6.3），再把分享標為 `accepted`。可重複呼叫；`dismissed` 的分享之後仍可接受。
- `dismiss`：只有收件者可以呼叫，且只能從 `pending`；已接受的回 `409 conflict`，已是 `dismissed` 的原樣回傳。
- `DELETE`：寄件者或收件者都可以呼叫，分享對雙方都消失。寄件者用來收回，收件者用來清理收件匣。
- 不是寄件者也不是收件者的帳號，對任何分享都得到 `404`。

**寄件者看不到被忽略**：在 `box=sent` 的列表與 `POST /shares` 的回應裡，`dismissed` 一律顯示為 `pending`，`respondedAt` 只在已接受時出現。寄件者只會知道「對方加入了書庫」，不會知道「對方忽略了」。

### 6.3 加入書庫

接受分享時，伺服器以一般推送的路徑（同一套合併規則、配額與序號）寫入：

- `kind = library`，`key = <workHash>`；
- 欄位 `addedAt`（現在）、`categoryIds = []`、`pinned = false`、`archived = false`、`updatePolicy = "auto"`；
- `deleted = false`；
- 所有時鐘都是 `<現在毫秒>:0:server`。

因為走的是欄位層級的 LWW：

- 作品已在書庫裡時，既有欄位的時鐘通常較新，這次寫入不會改掉使用者的分類或釘選；
- 作品曾被移出書庫時，較新的 `deleted = false` 會讓它回到書庫；
- 裝置時鐘明顯超前伺服器時，舊的刪除可能勝出，作品不會出現；這時 `inLibrary` 會是 `false`，使用者可再接受一次或在 App 內手動加入。

收件者的裝置透過平常的同步拿到這筆記錄，不需要為分享另外寫入書庫。超過配額時回 `409 quota_exceeded`，分享維持原狀態。

### 6.4 列表

- `box=inbox`（預設）列出收到的分享，`box=sent` 列出寄出的分享，都依建立時間新到舊。
- 每筆分享附完整的作品描述（含 `sourceName`、`repositoryUrl`），App 在使用者沒安裝對應套件時，用它顯示套件名稱與儲存庫網址引導安裝。
- `inLibrary` 是「這部作品現在在不在**呼叫者**的書庫裡」。
- `pending` 是收件匣中等待回應的數量，不受篩選條件影響；`GET /api/v1/shares/summary` 只回這個數字，給徽章用。
- 第一版沒有即時通知：網頁在載入與切換頁面時查詢，App 在每次同步循環時查詢。

## 7. 帳號刪除、停權與匯出

- 刪除帳號時，該帳號的追蹤、封鎖與所有寄出、收到的分享一併刪除（外鍵 `on delete cascade`）。
- 停權的帳號搜尋不到、不能被追蹤或分享；它既有的追蹤與分享保留，解除停權後恢復。
- 帳號匯出（`GET /api/v1/me/export`）多一個 `social` 區塊：接收設定、追蹤中、追蹤者、封鎖名單、寄出與收到的分享（寄出的分享同樣套用 6.2 的遮蔽規則）。

## 8. 鎖定順序

社交相關的交易一律先鎖使用者資料列（多個時依 `id` 由小到大），之後才碰 `follows`、`blocks`、`shares`。接受分享時，寫入書庫（推送交易，鎖收件者的資料列）與更新分享狀態是先後兩個交易，不巢狀。
